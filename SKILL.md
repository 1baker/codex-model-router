# Model Selector

Minimize expected **total tokens to a verified result**, with correctness as a hard requirement. Account for prompt and context size, reasoning and output tokens, tool use, verification, and likely retries. If the user asks to minimize money or latency instead, optimize that measure across the complete task. The cheapest token price or shortest first response can still produce more work overall. Honor any model, quality, budget, or latency constraint the user specifies.

## Route the task

1. Identify the requested outcome, necessary tools and source material, uncertainty, number of interacting steps, consequences of error, and how the result can be checked. Decide what information must remain in context and what output length is actually useful.
2. Check the models **available to this Codex environment** before recommending a model ID. Prefer the active model picker or runtime catalog. If using Codex's local `models_cache.json`, extract only the relevant `fetched_at`, model IDs, visibility, and effort fields; avoid dumping the full cache. Treat `visibility: list` as listed, not as proof of live entitlement, and do not route to hidden entries. Use [current Codex model guidance](https://learn.chatgpt.com/docs/models) and the [OpenAI model catalog](https://developers.openai.com/api/docs/models) when capabilities or pricing may have changed. Decide in the current turn when possible; a separate classifier run can consume more context than it saves.
3. Select the model and reasoning effort expected to use the fewest **total** tokens while passing the task's real verification. A stronger model may finish with fewer reasoning/output tokens or retries. Current starting points are:

   | Work | Starting choice |
   | --- | --- |
   | Short, fully specified extraction, formatting, or classification with easy checks | GPT-5.6 Luna, none or low |
   | Routine coding, document work, or research with bounded decisions | GPT-5.6 Terra, low or medium |
   | Difficult focused debugging or analysis where a cheaper attempt is likely to need rework | GPT-5.6 Sol, medium or high |
   | Hard end-to-end, cross-system, ambiguous, or consequential work needing strong judgment | GPT-6 Astra, medium or high |

   These are heuristics, not a required ladder. Choose a stronger model at the start when the failure cost warrants it. Astra does not support `none` reasoning. Do not assume higher effort always improves a task. For a consequential or repeated workload, prefer representative task results over a generic benchmark ranking; match any benchmark to the actual work before using it.
4. Keep the prompt, retrieved context, and exposed tools relevant; request only the response detail needed and use meaningful verification. Reassess the choice when the task or evidence shows that the current model is too weak, too costly, or using unnecessary reasoning effort. Switch up or down when the expected benefit exceeds the cost of switching; do not wait for a failed attempt when the mismatch is already clear. Where usage data exists, compare **total** input, cached input, reasoning/output tokens, retries, latency, and outcome across representative tasks before changing a standing default.

## Apply the choice

For a new Codex CLI or `codex exec` run, pass the chosen model with `-m` and set `model_reasoning_effort` for that run when needed. The host's initial model is a starting choice, not an instruction to keep it. If reassessment shows it is wrong for the task, **switch the existing chat when an agent-callable control is available**, then verify the accepted change and the model used by subsequent inference. Do not restart or fork the chat to claim an in-place switch.

In a Codex app-server host, a client can set `model` and `effort` on `turn/start` for an existing thread and subsequent turns. For a **running turn**, Codex 0.154.0 exposes experimental `turn/settings/update` with the current `threadId`, `turnId`, chosen `model`, and `effort`; it requires the host's `step_model_switching` feature. An `applied` response publishes settings for later steps in that turn, but does not change already captured steps or guarantee another inference occurs. `targetUnavailable` or a protocol error is not a switch. The host must expose this active-turn request to the agent through a trusted control tool or broker connected to the **same** app-server instance; a separate app-server process cannot change a live CLI chat. Verify the actual later model from per-request runtime events or traces when available; a thread summary may still show its initial model after a live-turn switch. A client can use `thread/settings/update` for future turns, but that is not an active-turn switch.

On this installation, launch a **new** interactive managed chat with `codex-model-host start` or `codex-model-host` and enter the first prompt, ending with a line containing only `.`. The global `modellabs route` command previews a prompt choice, while `modellabs start` submits the first turn without a TUI. ModelLabs reads the original prompt before any model call, checks the live host catalog, selects model and effort, disables unrelated configured MCP servers for that new thread, and submits the original text unchanged. This is a context-efficiency choice, not a permission grant; later needs may require starting a differently scoped chat until per-thread tool expansion is supported. `codex-model-host resume THREAD_ID` can attach the **same saved conversation** to the managed host only after its standalone TUI has exited. The launcher requires the exact UUID and refuses a resume while a standalone process has that rollout open. This handoff does not switch a still-running standalone process in place.

The `codex-model-host` launcher connects its TUI to the authenticated ModelLabs ingress proxy. For every later text `turn/start` on that connection, the proxy chooses model and effort **before forwarding** the turn to the host and adds a concise tool shortlist. A verified test routed two turns of one thread to Luna and then Astra. Configured MCP servers are scoped when a new thread starts; Codex 0.154.0 has no per-turn API for changing the attached MCP set, so later shortlists guide tool choice but do not alter availability. Explicit model instructions in the prompt and `modellabs --model` at creation take precedence over heuristics.

The globally trusted `UserPromptSubmit` hook also runs as a prompt front desk in Codex sessions that load it. For an active turn on the **same managed host**, it can submit the route through `turn/settings/update`; the host may reject incompatible model transitions, and an `applied` reply affects only later inference. The hook reads recent local transcript context for very short continuation prompts, keeps the original prompt unchanged, and logs only a hash plus routing metadata. In an ordinary standalone local chat, it can recommend a model and relevant MCP servers but cannot change the model or attached tool definitions; do not describe that as a successful switch. The hook does not retroactively run on a prompt already being processed, and older processes may need to reload hooks before it runs. For genuine before-inference model and MCP selection on **every** turn in an existing standalone chat, the owning host must expose the current session to ModelLabs or route its `turn/start` through the proxy. A `thread/read` status of `notLoaded` on the shared host means it sees only saved history, not the active standalone process; never resume the same thread concurrently just to claim a switch. Changing a local CLI wrapper or skill cannot alter a process already running outside that boundary.

In a managed chat, obtain the exact current ID from the shell's `CODEX_THREAD_ID`, then call `modelControl.switch_current_turn_model` with that `thread_id`, the selected `model`, and optional `effort`. The tool checks the host catalog, requires the thread and turn to be active on this host, and requires an ID-discovery command in that turn. It only reports that later steps were updated; use per-request evidence when claiming the model actually handled a later step. A regular local `codex` chat does not share this host and the tool must reject it.

In an interactive CLI, `/model` is a user interface control. Do not claim the agent invoked it unless the host actually offers an agent-callable equivalent. If the current integration has no such control, state the limitation briefly and continue the authorized work on the current model. Do not claim a switch happened or start a duplicate Codex session solely to simulate one.

When model selection is part of a larger task, state the choice and one short reason only if it helps the user understand a material cost or quality tradeoff. Otherwise proceed with the task.
